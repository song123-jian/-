# 桌面端 UI 体系重构融合实施方案

> 日期：2026-10-25  
> 适用对象：价格查询桌面端 v1.7.9，PySide6 / Qt Widgets，`source/ui/` 及其直接 UI 测试  
> 范围：仅桌面端；不规划移动端页面结构  
> 方案状态：待实施；本文件为方案交付，不代表 UI 重构已开始

## 1. 融合结论

以《UI体系重构方案-20261025.md》作为主稿，吸收上一版方案中的分阶段治理、迁移兼容、团队周期估算与验收门禁。采用以下决策：

| 主题 | 融合决策 | 理由 |
|---|---|---|
| 技术栈 | 继续 PySide6 / Qt Widgets，不进行 QML、Electron 或 C++ 重写 | 当前主表、任务池、打包与测试链均依赖 Qt，换栈会扩大成本和回归面 |
| 设计与组件 | 在现有 `theme_tokens.py`、QSS、`BaseDialog`、Model/View 之上增量补齐，不一次性重建设计系统 | 保留现有基础，组件只从已验证的重复模式中抽取 |
| 迁移主线 | 规范与基线 → 组件试点 → 主窗口拆分 → 对话框逐项迁移 → 主题/DPI 整理 → 灰度验收 | 沿用主稿的模块化顺序，并在每个阶段加入可停止、可回退的门禁 |
| 视觉范围 | 第一阶段保持现有亮色外观和交互语义；有独立需求及验收价值时再评估暗色主题 | 避免将结构性重构与视觉换肤绑在一起 |
| 组件抽象 | 不预先承诺 DataTable、NoticeBus、ConfirmController 等完整公共框架；先选一个具体场景验证 API | 避免尚未证明复用价值前过度抽象 |
| 资源构建 | 暂时保留现有 qrc 与 `resources_rc.py` 生成/跟踪方式；先记录构建链事实，再单独评估是否调整 | 移出 Git 会改变源码构建和发布流程，不是 UI 重构的必要前置条件 |
| 量化门槛 | 先采集当前可重复基线，再设性能阈值；行数、覆盖率作为趋势指标，不作为单独的发布硬门槛 | 可测性和用户任务成功优先于人为代码行数目标 |

## 2. 当前基线与需修正的事实

方案附件中的模块行数与当前工作区不完全一致。当前 `main_window.py` 为 1607 行，`dialogs.py` 为 928 行，`inventory_dialog.py` 为 580 行，`customer_dialogs.py` 为 231 行；工作区存在用户未提交改动，实施启动时必须对照实际基线重新记录，不应把这些数字视为稳定值。

当前源码确认的事实：

- 主窗口最小尺寸已设置为 960×640，并在启动时按屏幕可用尺寸调整；因此“无最小尺寸约束”不是当前事实。仍需实测多 DPI 与较小可用工作区下的布局行为。
- 主报价表使用 `QTableView` / Model-View；其他列表和台账混用 `QTableWidget` 与 `QTableView`，不能概括为“其余全部 QTableWidget”。按数据规模、排序、编辑和刷新方式逐处决定是否迁移。
- 当前目录下有 12 个 Qt 测试文件；`desktop_main.py` 中可见 17 个打包 smoke runner 类型，但打包入口按 acceptance 标记选择一个 runner，并不由单次调用自动全量运行。需逐项运行，或另行验证一个聚合入口。
- 当前存在主窗口和库存对话框中的局部 `setStyleSheet`；全局 QSS 与 token 模板已存在，令牌体系有扩展空间。
- 主稿中列出的 20,000 条报价、500 客户、像素级差异、主窗口 ≤300 行、组件覆盖率 ≥80% 均未证明来自现有业务数据或稳定基线；先做测量与任务验收定义，再决定适用门槛。

本方案不把未做的视觉走查、性能测试或真实程序验收描述为已完成。

## 3. 目标、范围与完成定义

目标是让桌面 UI 的页面边界、公共交互、样式规则和验证方式更容易维护，同时保持现有业务行为和用户熟悉的亮色界面。

范围包括：

- `source/ui/` 中主窗口、对话框、表格、委托、主题令牌和 QSS 的渐进整理；
- 直接受影响的 `source/tests/qt/` 测试及必要的定向 smoke 验收；
- 按桌面实际窗口进行的可用性、缩放、性能和灰度验收。

不包含：

- 移动端页面或跨端 UI 重写；
- 业务规则、服务层、存储结构、Supabase 数据和权限调整；
- 未经单独评估的主题换肤、构建/资源打包链改造及全应用视觉重设计；
- 以降低断言、删测试或改变业务流程来满足重构指标。

阶段完成必须满足：目标模块行为通过对应 Qt 与服务测试；用户关键流程无回归；增量审查无未处理的高置信度问题；失败时能回退到最近稳定模块；当前阶段的实际测试范围和未覆盖项均有记录。

## 4. 组件与设计系统方案

技术栈保持 PySide6 / Qt Widgets，不增加 UI 皮肤库或非必要依赖。

设计令牌按现有结构渐进补充：

- 保留当前颜色常量及其键名，新增语义色别名；不一次性迁移所有调用点。
- 补齐经重复场景确认的间距、字号、行高和交互状态 token；先覆盖本次迁移触及的组件。
- 亮色主题保持为默认，布局与控件视觉变化需作为独立差异审查。
- QSS 可按维护需要拆分，但先验证打包资源、开发态回退和构建产物一致性，不要求立即切换构建期生成。

公共组件采用“真实消费场景驱动”：

- 表格：选一个数据结构简单、风险低且真实存在排序/选择/编辑需求的列表做试点；验证列定义、选择行为、空态和加载状态后，再评估抽象是否适用于其他表。
- 空态/加载态：先统一重复文案与状态切换约定；只有出现至少两个明确消费者且 API 可复用时再抽组件。
- 通知：梳理 notice、状态栏、同步状态等语义和优先级；统一路由时保持当前信息驻留时间和关键错误可见性。
- 确认流：保留删除客户的网络不确定结果核对语义，不把业务特有的补偿与核验逻辑强行泛化到所有写操作。
- 表单字段与筛选条：重复结构稳定且至少被两个实际页面使用后再抽取。

## 5. 分阶段实施路线

周期按一个 2–3 人协作小组估算；单人顺序实施约 9–12 周。阶段时间是工程量估计，不含业务插单等待；完成一阶段后按真实差异调整后续排期。

| 阶段 | 优先级与周期 | 工作内容 | 交付物与门禁 | 主要风险与控制 |
|---|---|---|---|---|
| 0. 基线与规范 | P0，约 1 周 | 固定本轮文件/测试基线；绘制 UI 模块与调用边界；归纳间距、字号、颜色、通知、空态和键盘规则；记录桌面分辨率/DPI 矩阵 | UI 规范短文档、模块迁移表、当前截图/性能与关键任务基线、对应测试映射；未取得基线前不改视觉或性能门槛 | 当前工作区有未提交变更；冻结本轮比较基线并区分已有改动，避免把其归入重构差异 |
| 1. 组件试点 | P0，约 1–2 周 | 选一个低风险列表或重复状态模式建立小组件，迁移一个消费者验证；补必要的组件行为测试 | 一个真实消费者完成迁移；组件 API 与原页面行为一致；相关测试通过后才批准复用 | 组件过度泛化；试点证明复用价值不足时保留页面局部实现 |
| 2. 主窗口拆分 | P0，约 2–3 周 | 先抽客户目录与报价查询页面边界，再拆项目进度、引导、同步状态等明确区域；主窗口保留应用级装配与路由 | 每个子模块单独 PR；信号、状态与异步任务边界文档；对应 Qt/UI 与服务用例通过 | 用户改动集中于主窗口；拆分前逐段比较当前文件版本，避免覆盖并发改动；一次只迁一个边界 |
| 3. 对话框迁移 | P1，约 2–3 周 | 逐个整理客户、库存、项目进度、业务单据、图片报价和报价/导入对话框；仅在符合 Model/View 需求时迁表格；拆分 dialogs.py 的职责 | 每个迁移对话框保持公开调用接口或同步更新所有直接调用；对应 Qt 测试与业务回归通过 | 核心报价/导入流程风险高，排在低风险窗口之后；接口变更独立提交，避免与 UI 拆分混杂 |
| 4. 主题与 DPI 整理 | P1，约 1–2 周 | 把受影响文件中的局部样式迁入 token/QSS；检查自绘几何、对话框可用屏幕约束与 100/125/150% DPI；保留亮色视觉基准 | 样式来源与 token 规则；关键窗口在目标桌面视口和缩放比例下通过检查；主题构建及资源校验通过 | 像素截图易受字体、系统主题和渲染环境影响；用关键区域/状态对比加人工走查，不承诺不同机器像素完全相同 |
| 5. 灰度与验收 | P0，约 1 周 | 用便携版本或受控内部用户验证；比较崩溃/错误日志、关键任务步数和时长；准备回滚包 | 灰度报告、版本与文件哈希、关键任务验收结果；无 P0/P1 UI 回归且实际目标程序可用后才进入常规发布流程 | 灰度数据样本可能不足；至少覆盖一次完整导入与导出流程及项目进度查看/编辑，未覆盖链路明确列出 |

阶段 0–2 是首个可独立交付里程碑，约 4–6 周；全路线按团队规模约 8–11 周。以上估算比附件略收紧了暗色主题和资源迁移范围，但为性能/DPI基线与灰度保留了时间。

## 6. 增量迁移、兼容与回滚

1. 每个 PR 只处理一个页面、对话框或清晰的组件消费者；避免长寿命大分支，短分支建议不超过一周。
2. 新旧实现只在一个可控迁移阶段短暂并存；消费者通过既有调用边界切换，验收后及时删除旧实现。只有外部或广泛测试接口确需过渡时才保留兼容转接，并标注删除条件。
3. 保持服务/Store 调用点、信号语义和数据结构不变。必须调整业务接口时单独提交并独立验证。
4. 每个阶段保留可构建版本或明确 Git tag/commit；出现行为漂移时回退对应 PR/模块，不用额外补丁掩盖失败。
5. UI 变更不触碰用户数据、云端数据或迁移；验证优先用既有隔离数据目录和合成数据。构建或灰度需要外部业务写入时，另行按相应授权与隔离要求执行。
6. 保持现有 EXE 入口和默认亮色主题；资源编译、安装包覆盖和回退操作依照项目现有发布流程，UI 结构重构本身不要求替换正式 EXE。

## 7. 验收指标

### 功能与回归

- 每个 PR 运行该模块直接相关的 Qt/UI 测试和业务服务测试；共享主窗口、公共组件或核心报价/导入路径变更时，增加必要的关键回归。
- 当前 12 个 Qt 测试文件作为候选测试资产；运行范围按改动和有效测试交接记录确定，不要求每个 PR 重复全量运行。
- 17 类打包 smoke runner 视为 17 种可选验收场景，不视为一个现成的聚合测试。阶段/发布验收按覆盖矩阵逐项运行适用 runner；若需聚合执行，先实现并独立验证聚合入口。
- 五项关键用户任务：查价、改价、导入、导出、客户回收站往返；记录完成率、关键错误、操作步数和耗时，与阶段 0 基线比较，不得降低任务成功率。

### 视觉与桌面适配

- 关键窗口覆盖项目当前支持的桌面分辨率和 100%、125%、150% 缩放比例；检查窗口最小尺寸、控件裁切、表格横纵滚动、键盘焦点和弹窗可达性。
- 亮色主题下的关键页面对比允许抗锯齿与字体栅格差异；差异超出可接受范围时人工核验，不能仅凭像素阈值判失败或通过。
- 颜色对比度目标以 WCAG AA 作为新/修改文本样式参考；遗留区域在修改时逐步纳入，不将其作为本轮全项目强制迁移条件。

### 性能

- 阶段 0 先在同一机器、同一运行模式、固定合成数据集上建立冷启动、首次查询、过滤、页切换、客户目录操作与内存基线。
- 初始性能门槛建议：重构后冷启动和内存不比基线上升超过 10%；关键交互 P95 不超过基线的 1.2 倍；主线程不得因 UI 组装新增可复现的阻塞。阈值经基线重复性验证后冻结。
- 20,000 行报价和 500 客户只在现有业务规模或产品容量目标支持时作为压测数据集；主表首帧 ≤2 秒、过滤 P95 ≤500 毫秒等绝对值须先由当前程序实测确认可达。

### 可维护性

- 每次迁移后的模块职责和直接依赖可说明；主窗口负责装配/路由，不继续新增页面细节。
- 局部 `setStyleSheet` 与几何硬编码作为趋势指标逐步下降；仅在受影响范围内新增代码不得引入未经说明的样式逃逸。
- 组件测试覆盖关键行为分支；不以覆盖率百分比替代消费者测试和实际 UI 验收。`main_window.py ≤300`、每文件 ≤500 行可作为参考目标，不单独作为完成门槛。

## 8. 协作、版本与发布

- 设计系统负责人：维护 token/QSS 规则、组件 API 与视觉基线。
- UI 迁移负责人：按映射表逐模块拆分并维护旧接口兼容。
- 验收负责人：维护 Qt 测试映射、桌面视口走查、性能基线和灰度报告。单人实施时由同一开发者按阶段顺序承担。
- 每周一次短评审确认组件 API、迁移顺序与风险；迁移表是进度记录来源。
- 使用 trunk-based 或短寿命 `codex/` 分支；每个 PR 附本次差异审查、直接测试命令/结果和未覆盖链路，不附无关全仓检查结果。
- Git tag 按实际稳定里程碑命名；版本号变化由产品发布策略决定，不预设 UI 内部整理必须升级 minor。
- 灰度先覆盖可并行运行的便携版本；安装包发布前保留上一稳定安装包和核验过的回退流程。用户数据目录迁移与 UI 发布分开管理。

## 9. 实施前置检查与交付步骤

1. 建立本次实施的 Git/文件基线，定向记录受影响文件、直接测试、当前 EXE 版本及关键页面截图；有未提交改动的文件先比较并排除并发冲突。
2. 固化规范和映射表，确认阶段 1 的单一试点消费者、验收任务及数据集；只有这些证据齐备后进入组件实现。
3. 每个模块变更按“测试交接读取 → 单模块实施 → 实际程序 UI/行为验证 → 增量差异审查 → 更新项目和测试交接”闭环；结果通过后再进入下一模块。
4. 视觉/DPI 阶段按支持的桌面视口逐项检查；未取得实际窗口证据的情形标注未验证，不以静态代码或离屏截图代替。
5. 阶段验收通过后打稳定 tag，灰度用户运行一个完整业务周期，核对关键任务与错误趋势；如有 P0/P1 回归则暂停发布并回退相应阶段。

## 10. 方案风险与尚待测量事项

- 当前工作树并非干净，且主窗口、样式、测试等文件存在既有修改；实施者需先确定哪些变更已交付、哪些仍在进行，不能直接按附件旧行数或旧行号操作。
- 客户目录缓存与项目进度 UI 是近期变更的直接影响区域；后续拆分需复用其当前接口、滚动/编辑行为和异步边界，并以最新测试交接的有效结果为基准。
- 主稿中的暗色主题、全局清零行内样式、资源文件迁出 Git、高覆盖率与严格行数限额均可能产生额外维护成本，必须由具体维护问题支撑后再纳入单独阶段。
- 本轮未重新运行测试、未启动 EXE、未采集截图；该方案需在正式实施前重新确认当前 UI 状态和已提交版本。

## 11. 融合评分依据

本融合方案按同一评审维度自评 **91/100**：桌面端覆盖 19/20、源码事实准确度 22/25、实施可执行性 23/25、兼容与回滚 18/20、验收可验证性 9/10。与附件相比，主要提升是修正尺寸、表格、测试入口等事实，并将难以验证的绝对指标改成先基线后冻结；仍需在正式实施前取得当前屏幕适配、性能和目标用户任务数据，因此不评为满分。
