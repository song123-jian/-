# 桌面端 UI 体系重构方案

> 日期：2026-10-25 · 对象：价格查询桌面端 v1.7.9（`source/ui/`，PySide6 / Qt Widgets）
> 目标：在不中断业务的前提下，将现有 UI 重构为"设计系统 + 组件层 + 模块化页面"的可演进架构

---

### 1.2 必须承认的现有优势（重构的地基，不推倒）

1. **设计令牌雏形已建立**：[theme_tokens.py](../source/ui/theme_tokens.py) 的 40 色板（松烟绿）+ `apply_theme()` 的 `{{token}}` QSS 模板替换机制，是设计系统的正确起点。
2. **BaseDialog 统一对话框骨架**：content/footer/notice/busy 四件套 + `button()/label()` 工厂，17 个对话框中绝大多数已复用。
3. **主表是标准 Model/View**：QTableView + QuoteTableModel + QSortFilterProxyModel + 委托（[main_window.py:352-379](../source/ui/main_window.py#L352-L379)）。
4. **异步规范成体系**：TaskManager 读写分池、读可取消、双代次校验，UI 不冻结。
5. **行为快照回归网现成**：17 类打包 QA smoke runner（[desktop_main.py:97-131](../source/desktop_main.py#L97-L131)，由 acceptance 标记文件选择）+ 12 个 Qt 测试文件。**这是增量迁移最重要的安全网。**
6. 可访问性有意识：accessibleName/accessibleText/ElideRight/tooltip 已成惯例。

## 2. 分阶段重构路线图

总原则：**每个阶段独立可交付、可回滚；行为零变化的拆分先行，视觉升级最后。**

| 阶段 | 内容 | 优先级 | 交付物 | 周期 | 主要风险与规避 |
|---|---|---|---|---|---|
| **0 规范固化** | UI 规范文档、tokens v2、样式逃逸 CI 检查 | P0 | `docs/ui-spec.md`、tokens v2 代码、CI grep 规则 | 1 周 | 规范脱离实际 → 每条规范附现有代码反例，从现状归纳而非凭空设计 |
| **1 组件层建立** | components/ 公共组件（只建不迁） | P0 | DataTable、EmptyState、NoticeBus、ConfirmController、FilterBar、FormField + 单测 | 2 周 | 过度设计 → 只抽已出现 ≥3 次重复的模式（1.3 节 A/D 问题即需求清单） |
| **2 主窗拆分** | main_window 模块化（行为零变化） | P0 | CustomerPanel / QuotesPage / ProjectProgressPage / GuidePage / SyncBar，主窗 ≤300 行 | 2-3 周 | 拆分引入行为漂移 → 每拆一个面板跑对应 qt 测试 + 17 QA 全量 |
| **3 对话框迁移** | QTableWidget→DataTable、杂集对话框归位 | P1 | inventory/customer/business/quote 逐个迁移，dialogs.py 拆分 | 2-3 周 | 核心表单回归 → 迁移顺序按风险升序（见 §6.3） |
| **4 主题与适配** | QSS 分模块构建、暗色主题、弹性尺寸、DPI 审计 | P1 | build_theme.py、双主题、对话框 min/max 约束 | 1-2 周 | 视觉突变引发用户不适 → 亮色主题默认不变，暗色为可选项 |
| **5 灰度与验收** | 便携版灰度、指标采集、验收报告 | P0 | 灰度报告 + §5 指标全绿 | 1 周 | 灰度样本不足 → 复用现有便携 EXE + 安装包双通道分发 |

> 阶段 0+1+2 是"止血"主线（约 5-6 周），完成即可获得可维护性收益；3-5 可按迭代节奏插入。

## 3. 技术栈选型建议

### 3.1 总选型：保持 PySide6 / Qt Widgets，不换栈

| 备选 | 结论 | 理由 |
|---|---|---|
| **维持 PySide6 Widgets（推荐）** | ✅ | Model/View 已建立；TaskManager/QA 体系深度绑定 Qt 对象；PyInstaller+Inno Setup 打包链成熟；重构=结构调整而非重写 |
| Qt Quick / QML | ❌ | 全部 19 个模块重写；QA runner 与 QML 对象模型不兼容；团队需学新语言；收益（动效）非当前痛点 |
| Electron / Web 壳 | ❌ | 体积/内存劣化；离线单机定位受损；`static/app.js` 仅辅助页，不代表可迁移 |
| 换 C++/Qt | ❌ | 纯重写，无增量路径 |

### 3.2 组件库：自建轻组件层（不引入第三方皮肤库）

| 方案 | 与松烟绿 token 兼容 | 打包影响 | QA 兼容 | 结论 |
|---|---|---|---|---|
| **自建 components/（推荐）** | 完全继承现有 token | 零新增依赖 | 完全兼容 | 现有 BaseDialog/委托体系已证明自建可行，缺的只是补齐件 |
| PyQt-Fluent-Widgets | 强制 Fluent 视觉，token 冲突 | +数 MB | 可用 | 视觉推翻重来，违背"亮色不变"原则 |
| qt-material | 主题体系与 QSS 模板机制冲突 | 小 | 可用 | 两套主题引擎并存，维护更糟 |

自建范围（阶段 1 交付物）：
- `components/data_table.py`：QTableView 封装——声明式列定义、统一空态/加载态、排序、选择行为、右键菜单、行高从 SIZES 取；
- `components/empty_state.py`：图标+主文案+次文案+操作按钮的空态组件；
- `components/notice_bus.py`：统一通知路由（notice/statusBar/同步条三通道归一），替换 notice_source 手工切换；
- `components/confirm_controller.py`：把客户删除的"uncertain→核对结果"模式泛化为所有写操作可复用的确认流；
- `components/filter_bar.py` / `form_field.py`：筛选条与表单字段（label+控件+校验错误位）。

### 3.3 设计系统搭建（tokens v2）

三层令牌结构（在 theme_tokens.py 基础上演进，不推翻）：

```
primitive   #color/green-700 → 原始值（现 COLORS 的 40 个原样保留）
semantic    background / text-primary / price-up / danger …（业务语义命名）
component   table-row-height / sidebar-item-height / dialog-min-width …（组件级，替换 B3 的硬编码）
```

配套扩展：
- `spacing`: 4/8/12/16/24/32 阶梯；`typography`: 12/13/15/18/22px × regular/medium/bold（收编 main_window L272/L1055 的内联字号）；`radius`/`state`（hover/pressed/disabled）。
- **QSS 构建期生成**：新增 `build_theme.py`，在打包阶段把 token 注入 QSS 生成最终文件，替代运行时字符串替换；支持输出多主题（亮/暗）。运行时替换机制保留为回退。
- theme.qss 拆分为 `qss/base.qss / controls.qss / tables.qss / dialogs.qss`，构建期合并，消除 95 行单文件的规模增长压力。

### 3.4 样式管理规则

1. 全局 QSS 是唯一样式来源；inline `setStyleSheet` 清零（CI 用 `rg "setStyleSheet" source/ui/` 白名单检查，B2 三处率先迁移）。
2. 自绘 delegate（customer_delegate/quote_delegate）的几何尺寸一律从 SIZES 读取。
3. 图标继续走 Qt 资源（qrc），但 `resources_rc.py` 编译产物不入库（加入 .gitignore，构建脚本生成），消除 B5 双源。

## 4. 兼容性保障与增量迁移策略

**核心思路：以 17 类 QA smoke runner + 12 个 qt 测试为行为快照，组件双轨、模块小步、随时可停。**

1. **行为快照（迁移前固化）**
   - 阶段 0 补齐：每个待迁移模块先跑一遍对应 acceptance（如迁库存前固化 `acceptance-inventory.json` 输出），快照即基准。
   - qt 测试从"能跑"升级为"迁移门禁"：任何 UI PR 必须全绿。

2. **组件双轨期**
   - 新组件与旧实现并存于两个包（`ui/components/` vs 旧路径），**每个模块迁移完成即在同一 PR 删除旧路径**，不留兼容 shim，避免双轨永久化。

3. **模块小步迁移**
   - 每个迁移 PR 只动一个对话框/面板；PR 体积以"一天可审"为上限。
   - 迁移顺序按风险升序：customer_dialogs（207 行、纯只读+生命周期，测试最厚）→ inventory → business_document → image_quote → quotes/import（核心生产路径最后）。

4. **数据与 UI 分离护栏**
   - 拆分只搬 UI 代码，service/store 调用点不变；如需调整服务调用签名，独立 PR 处理，禁止与 UI 拆分混合。

5. **回滚预案**
   - 每阶段一个 git tag；便携 EXE 灰度期间保留上一版本下载链接；安装包升级路径不变（Inno Setup 覆盖安装可回退到旧版安装包）。

## 5. 验收标准与质量校验指标

### 5.1 功能与回归（硬门禁）
- `tests/qt/` 12 项全绿；17 类 QA smoke runner 全部输出 `passed`；
- 迁移模块逐一比对迁移前 acceptance 快照（结果集、提示文案、交互序列一致）。

### 5.2 性能指标（20,000 条报价 / 500 客户合成数据集，与重构前基线对比）
| 指标 | 目标 |
|---|---|
| 冷启动至主窗可见 | ≤ 基线 +10% |
| 主表首帧（全量数据） | ≤ 2s |
| 键入过滤至结果呈现 P95 | ≤ 500ms |
| 面板/页签切换 | ≤ 100ms |
| 峰值内存 | ≤ 基线 +15% |
| 删除/恢复客户后目录恢复 | ≤ 1s 且不丢滚动位置 |

### 5.3 可维护性指标（可量化、进 CI）
| 指标 | 目标 |
|---|---|
| main_window.py 行数 | ≤ 300 |
| ui/ 单文件行数 | ≤ 500（resources_rc 除外且不再入库） |
| inline setStyleSheet 数量 | 0 |
| QSS 中硬编码颜色（非 token）数量 | 0 |
| delegate 中硬编码几何尺寸 | 0（全部来自 SIZES） |
| components/ 单测覆盖率 | ≥ 80% |
| 对话框统一走 BaseDialog/components | 100%（login 按需豁免并注明原因） |

### 5.4 可用性验收
- 5 个核心任务脚本化走查（查价 → 改价 → 导入 → 导出 → 客户回收站往返），记录步数与耗时，**不劣于现状**；
- 亮色主题下关键页面截图对比 diff ≤ 阈值（像素级保证"看起来没变"）；
- 暗色主题全页面人工走查一轮 + 对比度抽检（正文 ≥ 4.5:1）。

## 6. 可落地实施步骤

### 6.1 阶段 0：设计规范统一（操作指引）
1. 从 1.3 节问题清单归纳《UI 规范》：间距阶梯、字号阶梯、颜色语义、控件状态、空态/加载态/错误态三态模板、确认流规范（含网络不确定模式）、通知分级（info/warn/error 的通道与驻留时长）。
2. tokens v2 落码：扩展 theme_tokens.py 三层结构，**原 COLORS 键全部保留**（40 处引用零改动），新增语义/组件层。
3. CI 加样式逃逸检查：`rg -n "setStyleSheet" source/ui/` 输出必须为空（白名单文件除外，白名单只减不增）。
4. 产出《模块迁移映射表》：每个旧模块 → 目标组件/新位置 → 对应 QA 标记文件 → 风险级。

### 6.2 阶段 1：公共组件抽离
1. 按 §3.2 清单逐个实现，每个组件先写测试（`tests/qt/components/`）再写实现。
2. DataTable 验收样例：用客户只读历史（CustomerDetailDialog 数据形状）做首个消费场景的预演，但**不在本阶段替换线上代码**。
3. 组件 API 评审一次（字段命名、信号签名），冻结后进入阶段 2。

### 6.3 阶段 2-3：逐模块迁移
**主窗拆分顺序**（每步一 PR，跑 test_desktop_ui + 全量 QA）：
1. CustomerPanel（边界最清晰：meta_loaded/customer_search_changed/select_customer/manage_customers 四方法 + 目录视图与模型）；
2. FilterBar（筛选区 7 控件 + debounce）；
3. GuidePage / ProjectProgressPage（静态内容为主，风险低）；
4. SyncBar（sync_label + 定时器 + 状态机）；
5. 主窗残留（托盘、页面路由、任务分发）收纳为壳。

**对话框迁移顺序**：customer_dialogs（QTableWidget×2 → DataTable，首战立标杆）→ project_progress → inventory → business_document → image_quote → dialogs.py 拆分（BaseDialog 独立成 `components/base_dialog.py`，QuoteDialog/导入/导出/设置各归其位）。

### 6.4 阶段 4：主题升级
1. `build_theme.py` 生成 QSS，`apply_theme()` 改为加载生成产物（保留运行时替换回退一代版本）；
2. 暗色主题 = semantic 层第二套映射，组件层不变；设置页加主题切换（跟随系统/亮/暗）；
3. 对话框尺寸策略改造：`BaseDialog(w,h)` 语义改为"建议尺寸"，统一定义 min/max 约束，消除写死尺寸；
4. 125%/150% DPI 下全页面走查自绘委托。

### 6.5 灰度发布
1. 便携 EXE 先行（用户群小、可并行旧版、`--data-dir` 隔离验证）；
2. 采集 `data/app.log` 错误码（workers.py 已按 error_code 分类记录，直接复用）对比重构前后分布；
3. 灰度 ≥ 1 个业务周期（含一次完整导入+月度导出场景）无 P0/P1 再发安装包；
4. 发布说明明示"视觉零变化，内部结构升级"，降低用户预期扰动。

## 7. 团队协作与版本管理

### 7.1 分工建议

**1 人配置**（现状最可能）：按阶段串行，0→1→2 为一个里程碑，中途不打断业务需求；业务需求与重构冲突时，重构让路但 CI 样式检查不豁免。

**2-3 人配置**：
| 角色 | 职责 |
|---|---|
| 设计系统 owner | tokens/QSS/组件 API/规范文档（阶段 0-1 主力，此后守门） |
| 模块迁移 | 阶段 2-3 逐模块 PR，遵守映射表 |
| 验收自动化 | qt 测试补齐、QA 快照固化、性能基线脚本、灰度报告 |

协调机制：每周一次 30 分钟组件 API 评审；迁移映射表是唯一事实源，进度在表上更新。

### 7.2 版本管理策略

1. **trunk-based + 短命分支**：迁移分支生命周期 ≤ 1 周，禁止长存的大爆炸 rewrite 分支。
2. **PR 门禁**：对应 qt 测试 + 对应 QA runner 输出贴在 PR 描述；样式逃逸检查必须绿。
3. **版本号**：重构序列走 1.8.x（minor），每个阶段完成打 tag（`ui-refactor-stage2` 等）；亮色视觉不变承诺写入 CHANGELOG。
4. **资源文件**：`resources_rc.py` 移出 git 跟踪后，qrc/图标走构建脚本；二进制（EXE/安装包）沿用现有 Git LFS 方案。
5. **回滚纪律**：任何阶段发现行为漂移，优先回退该模块 PR 而非打补丁掩盖；快照对比失败即阻断发布。

## 8. 一页纸总结

```
现状：地基好（token/BaseDialog/Model-View/QA 快照网），上层乱（巨石主窗、表格双体系、

验收：性能不劣化、亮色像素不变、main_window≤300 行、inline 样式=0、覆盖率≥80%。
周期：止血主线（阶段 0-2）约 5-6 周；全量（0-5）约 9-12 周，可按迭代拆散。
```
