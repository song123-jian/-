# 注册后台初始化方案

目标项目：`saodtwnvbanjlkwwivcb`。此前缺少本程序结构、注册入口返回404；用户明确授权后，回滚演练、正式初始化、pmu-register部署和最终核验均已完成。下列SQL保留作实施来源记录，不应重复执行。

## 已准备文件

- `初始化注册后台.sql`：按项目现有迁移顺序合并，在单一事务内建立兼容基础表、个人账号与个人报价表、RLS、注册触发器及总数限制。检测到任何现有 `pm_`/`pmu_` 表、函数或 `pmu_executor` 角色时拒绝执行；不覆盖现有程序结构。
- `初始化回滚演练.sql`：同样初始化后，在事务内以无密码临时行验证重名拒绝、15 个账号上限、停用仍占名额、第 16 个账号原子回滚，最后 ROLLBACK；不保留测试账号。
- `backend-sources.json`：组成脚本的 7 个源码文件 SHA256，已与本机源码核对。
- `index.ts`：已有 `pmu-register` 注册函数源码副本。服务端管理凭据由 Supabase 运行环境读取，不写入客户端、本文或聊天。

## 执行顺序与边界

1. 已取得本项目初始化和公开注册接口部署的明确授权。
2. 在目标项目执行回滚演练一次；检查输出 `duplicate_and_total_15_limit=passed`，并只读确认事务结束后无程序表或测试账号残留。演练失败则不执行正式初始化。
3. 正式执行 `初始化注册后台.sql` 一次；最终只读确认版本 `1.7.3`、账号总数 0、总数限制 15 和客户端无注册检查 RPC 权限。
4. 部署 `pmu-register`，关闭该函数的旧 JWT 网关校验（项目 `source/supabase/config.toml` 已设置 `verify_jwt=false`）。自助注册时尚无用户 JWT，publishable key 也不是 JWT。其他函数和业务权限保持原配置。
5. 使用不创建账号的无效输入检查函数响应。用户随后在客户端自行注册，成功注册及自动登录仍需在真实链路完成验证。

这里的 15 个账号指本程序的 `pmu_members` 总数，含停用账号。用户名会去首尾空格并转小写；现存用户名及其 Auth 邮箱不可重复。数据库唯一约束和事务锁负责最终拒绝并发超额注册；其他应用的 Supabase 用户不计入这 15 个名额。

初始化仅写入空程序结构、版本配置和权限，不导入客户、报价或既有账号，不修改已有账号密码。正式初始化后，如需撤销，应先停止自助注册并人工核对实际用户数据；不提供会删除账号或业务表的自动清理脚本。

pmu-register完整源码回读与本地一致后部署成功，专用旧JWT校验关闭并保存。实际GET返回405/method_not_allowed，无效用户名及空密码分别返回400/invalid_username和400/invalid_password。上述接口验证未创建账号；真实成功注册和自动登录仍由用户自行验证。最终桌面程序已更名“工作”1.7.4，后端注册限制版本1.7.3继续适用。
